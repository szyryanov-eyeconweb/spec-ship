# Bug Fix

Вход — **симптом**, не требование. Скилл выясняет, каким поведение задумано, находит корень, оценивает радиус поражения и производит `Diagnosis` + обычный `TaskSpec` в `.ship/pipeline/{slug}/`. Код не пишет — фикс собирает `build` по TaskSpec.

Заменяет `shape-doc` + `decompose` на баг-входе. Не добавляется к ним: на баге TO-BE не шейпится в интервью, а **выясняется** из канона, ADR и dev. `build` и `review` дальше идут без изменений.

## Отличие от фича-пайплайна

| | фича | баг |
|---|---|---|
| Вход | требование (WHAT известен) | симптом (WHAT = «как задумано») |
| TO-BE | шейпится в интервью | выясняется из workflow-доков / ADR / dev |
| `survey` | опционален | **обязателен** — якорь всегда в существующем коде |
| Разбивка | N вертикальных слайсов | обычно 1 TaskSpec (корень один) |
| Первый тест | по `acceptance_criteria` | **репро-тест до анализа** |
| Главный риск | недопонятое требование | симптом вместо корня + недочищенные sibling-callers |

Greenfield-ветки у бага не бывает: сломанного кода не существует без кода.

## Вход

```
/spec-ship:bug_fix «симптом; репро; якорь»
```

Три формы, все валидны:

| Форма входа | Действие |
|---|---|
| симптом + репро + якорь | якорь есть → сразу шаг 2 |
| падающий тест (`tests/Functional/PayoutTest::testFeeDeducted`) | прогнать, прочитать трейс → якорь из трейса |
| только симптом («у партнёра в отчёте не та сумма») | якорь неизвестен → **ГЕЙТ локализации** (шаг 1) |

Нет ни репро, ни якоря, ни способа наблюдать симптом → спросить пользователя и ждать ответа: диагностика опровергает гипотезы против наблюдаемого симптома, без него опровергать нечего.

## Процесс

### 1. Зафиксировать дефект

Записать четыре части (идут в `defect` артефакта):

- **symptom** — что наблюдаемо: неверное значение, исключение, отсутствующий эффект, падающий тест. Конкретно, с числами и именами.
- **repro** — как воспроизвести: шаги, команда, падающий тест, входные данные.
- **expected** — каким поведение задумано.
- **expected_source** — **откуда это известно**: `workflow-doc:<путь>` | `adr-NNN` | `bd-NNNN` | `dev` | `none`.

`expected_source: none` → **ГЕЙТ**: спросить человека «это баг или намеренное поведение?» и ждать вердикта. Поведение без источника ожидания может быть чьим-то контрактом — «фикс» сломает того, кто на него полагался.

**Якорь неизвестен** (третья форма входа) → **ГЕЙТ локализации**: перечислить 2–4 гипотезы «где симптом входит в систему» с обоснованием по коду, выбор оставить человеку. Весь survey стартует от якоря — ошибка здесь уводит весь анализ.

### 2. Survey (обязателен)

Вызвать скилл `survey`. Якорь = **точка симптома** (не предполагаемый корень — его ещё не знаем). Передать блок `defect` из шага 1 — survey положит его в `anchor.defect`.

Survey остаётся наблюдением: корень не объявляет. Что берём из его выхода:

| Поле survey | Роль здесь |
|---|---|
| `connected_groups[].symbols` | заготовка blast radius (шаг 5) |
| `risk_if_skipped` | чеклист «что ещё сломано тем же корнем» |
| `observed_workflows` | AS-IS = **улика**: расхождение с `expected` и есть баг |
| `validation_boundaries` | где живёт большинство багов: потерянная нормализация, невалидированный вход |
| `adr_refs` | «так задумано?» → ADR-CONFLICT вместо фикса |

`.ship/docs/workflows/INDEX.md` со `Status: current` survey читает сам — это **источник intended behavior**, заменяющий пустое интервью shape-doc. Канон говорит, как система должна себя вести; расхождение канон↔код формулирует баг без домыслов.

### 3. Репро-тест первым

**До любого анализа корня.** Вызвать `ship-red` через Agent tool: один падающий тест, воспроизводящий симптом на seam из шага 6 (или на ближайшем существующем seam области, если seam ещё не выбран).

Красный тест = баг существует и наблюдаем. Дальше диагностика опровергает гипотезы против него, а не против пересказа тикета.

| Исход | Действие |
|---|---|
| тест красный | → шаг 4 |
| **не воспроизводится** | **СТОП.** Нет репро — нет бага. Вернуть человеку: что пробовали, чего не хватает (данные? окружение? версия?) |
| `ship-red` вернул `blocked` | нет seam для наблюдения симптома → LOGIC-сигнал: дошейп seam с Dev, не догадка |

**Интермиттент/флик** (симптом воспроизводится не каждый прогон): репро-тест считается красным только после N прогонов с зафиксированной частотой (`defect.repro` фиксирует «K из N»). Один красный прогон из десяти — не репро, а совпадение. Частота идёт в `Diagnosis`, отдельной ветки процесса нет.

### 4. Root cause

Не «где симптом», а **где сломано допущение**. Записать гипотезы в `hypotheses[]`, каждую — с доказательством или опровержением по коду:

- гипотеза: что именно неверно и где (`путь#метод`)
- `evidence_for` / `evidence_against`: конкретные `файл:строка`, не рассуждения
- `verdict`: `confirmed` | `refuted` | `unresolved`

Опровергать активно: гипотеза, которую не пытались убить, не проверена. Первая правдоподобная ≠ корень.

Корень найден ⟺ ровно одна гипотеза `confirmed` и она объясняет **весь** симптом (все наблюдаемые части, не «в основном»). Частичное объяснение = корень не найден.

**Не найден за N гипотез** (N = 5) или все `unresolved` → эскалация, не догадка: отдать `Diagnosis` с гипотезами человеку. Догаданный фикс дороже нерешённого бага.

### 5. Blast radius

Корень найден → найти **всех**, кого он ломает. Стартовать от `connected_groups` survey, затем грепнуть всех вызывающих корневой символ — survey трассировал от симптома, а не от корня, и мог не покрыть сиблингов.

Для каждого вызывающего: сломан тем же корнем или нет, с обоснованием.

Правило фикса: **чинить в общей точке, где сходятся все вызывающие**, а не в пути из тикета. Один guard в общей функции — меньший дифф, чем guard в каждом вызывающем, и не оставляет сиблингов сломанными. Если общей точки нет — перечислить все места явно в `spec.files_to_change`, ни одно не «на потом».

Сиблинги, сломанные тем же корнем, но требующие отдельного фикса, → отдельный TaskSpec (шаг 7), не молчаливый пропуск.

### 6. Test seam + regression guard

Выбрать `spec.test_seam` по тем же трём правилам, что `decompose` (существующий seam > высший уровень > минимум seam'ов) — канон в `decompose/SKILL.md` шаг 2.5.

Репро-тест из шага 3 становится **постоянным** `test_scenarios[]` записью: `scenario: "sad"` (или `edge`), `input` из `defect.repro`, `expected_outcome` из `defect.expected`. Не временная проверка — регрессия, которая не должна вернуться.

Точные значения из симптома (суммы, ставки, пороги, идентификаторы) → `data[]` с `d-N`, как в `decompose`. «Отрицательный баланс −150.00 KRW» — это `data`-запись, не проза: фикстура собирается из точного значения, review сверяет посимвольно. Крупный вход, на котором симптом воспроизводится (дамп проблемных строк, набор транзакций), — файлом в `{slug}/data/` + дескриптор `value_ref`, не инлайном в артефакт.

### 7. Классифицировать trust_zone и нарезать

`trust_zone` — те же признаки, что в `decompose` шаг 3. Специфика бага:

- баг в persistence с миграцией данных, в деньгах/балансах, в безопасности/доступе → **`CRITICAL`** (агент = консультант, Dev пишет сам)
- корень найден, фикс декларативен, интерфейс не меняется → `ROUTINE`
- фикс требует промежуточных структур, правил reconciliation, или порядок восстановления данных неочевиден → `LOGIC` (скелет `shape` со `status: "proposal"`)

Число TaskSpec:
- **обычно один** — корень один, фикс один. Не изобретать вертикальные слайсы там, где их нет.
- **несколько** — когда blast radius дал сиблингов, требующих независимых фиксов, или когда фикс корня и очистка испорченных данных — разные задачи (второе часто `CRITICAL`).

Испорченные данные — **отдельный TaskSpec**, никогда не часть фикса кода: фикс останавливает порчу, миграция чинит накопленное. Разные trust_zone, разный откат.

### 8. Апрув диагноза (гейт, всегда)

Показать человеку **до** сохранения артефактов:
- симптом и его источник ожидания
- корень: подтверждённая гипотеза + доказательство
- отброшенные гипотезы (коротко — что опровергнуто)
- blast radius: кто ещё сломан, где чиним
- план: сколько TaskSpec, их `trust_zone`
- репро-тест: где живёт, что ассертит

Получить апрув. Диагноз без апрува не сохраняется: неверный корень стоит дороже всего дальше по цепочке.

### 9. Сохранить артефакты

Slug — по правилу из [CANON.md](../CANON.md). У бага нет BusinessDoc, поэтому `{slug}` = `{diag-id}-{kebab}`, где `kebab` — 4–6 слов из `defect.symptom`.

```
.ship/pipeline/{slug}/
├── survey-<diag-id>.json      перенести из _intake/ (survey шага 2)
├── diag-<YYYY>-<NNNN>.json    Diagnosis
└── task-<NNNN>-01.json        TaskSpec (обычная схема, ×N при сиблингах)
```

`TaskSpec.business_doc_id` = `null`, `TaskSpec.diagnosis_id` = id диагноза. `validation.business_doc_coverage` = `[]` (нет bd) — покрытие проверяется против `defect.expected`.

## Схема выхода

Перед шагом 9 открыть полную схему `Diagnosis` — [SCHEMA.md](SCHEMA.md). Схема `TaskSpec` — [decompose/SCHEMA.md](../decompose/SCHEMA.md), не дублируется: выход `bug_fix` — обычный TaskSpec, чтобы `build` не отличал баг от фичи.

## Что после

```
/spec-ship:build task-XXXX-01      без изменений (ROUTINE/LOGIC/CRITICAL как обычно)
/spec-ship:review build-XXXX-01    + check #6 regression_guard
после мёржа:
/spec-ship:adr-promote             если фикс родил ADREntry
/spec-ship:doc-promote-feature     ЕСЛИ баг вскрыл расхождение канона с кодом
```

Последнее обязательно, когда `expected_source` был `workflow-doc` и **док оказался неверен**: `Status: current` док, разошедшийся с реальностью, — источник следующего бага. Починить канон, иначе следующий survey прочитает ту же ложь.

## ADR conflict

Поведение противоречит `Status: Accepted` ADR — не чинить молча. Запустить [ADR-CONFLICT flow](../ADR-CONFLICT.md), `detected_by: bug_fix`. Специфика этапа:

- **ADR верен** → «баг» не баг, а нарушение допущения вызывающим: фикс переезжает на вызывающего, `defect.expected` переписывается под ADR.
- **ADR устарел** → ESCALATE + `AdrChangeTicket`, фикс ждёт вердикта maintainer'а.

## Гейты человека

| Гейт | Когда |
|---|---|
| локализация | якорь неизвестен из входа (шаг 1) |
| «баг или намеренное поведение?» | `expected_source: none` (шаг 1) |
| не воспроизводится | репро-тест зелёный (шаг 3) |
| корень не найден | N гипотез исчерпаны / все `unresolved` (шаг 4) |
| ADR-CONFLICT | поведение против `Accepted` ADR |
| апрув диагноза | всегда перед сохранением (шаг 8) |
| CRITICAL | как в `build` |

Сомнение «гейт или нет» → гейт.

## Правила

- Репро-тест **до** анализа корня. Диагноз без красного теста — гипотеза, не диагноз.
- Корень, а не симптом: фикс идёт в общую точку всех вызывающих. Залатанный путь из тикета оставляет сиблингов сломанными.
- `bug_fix` только диагностирует и режет. Ноль правок в `src/`; единственная запись — артефакты в `.ship/pipeline/{slug}/` (репро-тест пишет `ship-red`, не скилл).
- Каждая гипотеза несёт доказательство `файл:строка`. «Похоже, дело в кеше» — не гипотеза.
- Порча данных — отдельный TaskSpec от фикса кода, всегда.
- Точные значения симптома — в `data[]` с `d-N`, не в прозе.
- Сквозные законы (сохранить ВСЕ артефакты до отчёта, `[]` не опускать, состояния из `CONTEXT.md`, выборка ADR через INDEX) — [CANON.md](../CANON.md).
