# Shape Doc

Интервьюирует пользователя о фиче и производит замороженный артефакт `BusinessDoc` JSON, сохраняя в `.ship/pipeline/`.

## Процесс

### 1. Собрать контекст

- Прочитать `CONTEXT.md` (доменный глоссарий).
- Прочитать `.ship/docs/adr/INDEX.md` (НЕ все ADR). Отфильтровать строки `Status: Accepted` где `Area` пересекает область фичи. Загрузить тела ТОЛЬКО matched ADR. Expired игнорировать.
- Проверить survey: `.ship/pipeline/_intake/survey-*.json` и slug-директории по той же области. Если есть — `observed_workflows` и `connected_groups` задают контекст интервью: вопросы не «как сейчас работает?» (уже известно), а «что должно измениться?». Если фича меняет существующее поведение, а survey нет — предложить пользователю сначала `/spec-ship:survey` (не блокирующе).
- Проверить `run_handoff` из roadmap: если фича пришла из `.ship/roadmap/{epic}/ticket-NN.json` (передан путь handoff), прочитать его. `decisions[]` (их `resolution`) — уже принятые эпиком решения: НЕ переспрашивать, вносить как контекст/constraints. `in_scope`/`out_of_scope` — границы фичи: интервью держится внутри, не растаскивает и не сужает. `survey_ref` — готовая карта кода (эквивалент своего survey). `adr_refs` — уже выявленные картой ADR, догружать по INDEX. Roadmap решил ЧТО; shape решает детали КАК, не переоткрывая скоуп.
- Если ещё не сделано, запустить процесс шарпинга терминологии и выявления конфликтов с ADR.

### 2. Интервью (если нужно)

Если фича недоспецифицирована, выяснить:
- Кто акторы?
- Happy path? Edge cases? Sad paths?
- Явный измеримый Definition of Done?
- Constraints (инфраструктура, performance, ссылки на ADR)?
- Конкретные данные, управляющие поведением: ставки, матрицы, лимиты, шаблоны строк, справочные списки? Каждое такое значение — в `data[]` с точным значением, НЕ в прозе критериев. «Комиссия около 5%» — недоспецификация: выяснить точное значение или зафиксировать вопрос. Значение крупное (матрица на десятки строк, справочный список, длинный шаблон) — положить файлом в `{slug}/data/` и записать дескриптор `value_ref` (path, shape, sample, checksum) вместо инлайна: точность держит checksum, а корпус не поедет копиями через все TaskSpec.

Правило батчинга вопросов:
- продолжать разбор фичи через каждую новую неясность, копя связный батч вопросов
- стоп только когда батч готов ИЛИ неясность истинно блокирует дальнейший разбор
- каждый вопрос классифицировать: `blocking` (без ответа заморозка невозможна) | `non_blocking` (можно ехать под явным допущением — сформулировать допущение сразу)
- незакрытые вопросы фиксировать в `open_questions[]` артефакта, не терять в чате

Для ветвистых сценариев использовать компактный workflow-синтаксис в обсуждении и в `workflow`-полях артефакта:

```
состояние --шаг--> состояние [ветка 1, ветка 2]      # [] условные, () параллельные
{старый workflow} --шаг--> {новый workflow}          # фича меняет существующий код-путь
```

Канон нотации — [CANON.md](../CANON.md) («Workflow-нотация»), имена состояний из `CONTEXT.md`. Если есть survey и фича меняет наблюдаемый код-путь — `feature.workflow` писать рефакторинг-формой: `{имя из observed_workflows} --шаг--> {новый workflow}`. Это явно связывает AS-IS из survey с TO-BE и подсказывает doc-promote, какие workflow канона замещаются.

### 3. Прогнать Requirements Review

Перед заморозкой проверить:
- [ ] Все три типа сценариев покрыты: `happy`, `edge`, `sad`
- [ ] DoD измерим (не "работает корректно")
- [ ] Конкретные значения (ставки, пороги, матрицы, шаблоны) вынесены в `data[]`, а не размазаны по прозе given/when/then; критерии ссылаются на `d-N`
- [ ] Нет конфликтов с существующими ADR — перечислить в `conflicts[]` если найдены
- [ ] Акторы совпадают с доменным глоссарием в `CONTEXT.md`
- [ ] Нет `open_questions` с `severity: "blocking"` без `resolution` — иначе НЕ апрувить, собрать батч и спросить пользователя
- [ ] У каждого `non_blocking` вопроса без `resolution` сформулировано `assumption` — под каким допущением едем дальше

Найденный конфликт разрешается через [ADR-CONFLICT flow](../ADR-CONFLICT.md) (канон протокола), а не остаётся записью в списке. Детектор здесь = Requirements Review, `detected_by: shape-doc`, `task_spec_id: null`. BusinessDoc апрувится только после разрешения.

### 4. Произвести артефакт

Сгенерировать `BusinessDoc` JSON строго по схеме ниже.

Вывести slug директории фичи по правилу slug из [CANON.md](../CANON.md). Пример: `bd-2026-0002-db-connection-reconnect`.

Сохранить в:
```
.ship/pipeline/{slug}/bd-<YYYY>-<NNNN>.json
```

Взять `id` от пользователя или автогенерировать `bd-<год>-<4-значный-номер>`.

Поставить `status: "approved"` только после явного подтверждения ("approve", "ship it", "ок", "годится").

### 5. Подтвердить

Показать сохранённый путь (включая директорию фичи). Сообщить какие ADR были учтены и были ли найдены конфликты.

Если использовался survey из `.ship/pipeline/_intake/` — перенести его в `.ship/pipeline/{slug}/` и проставить в нём `business_doc_id`. Survey по фиче живёт рядом с её артефактами.
