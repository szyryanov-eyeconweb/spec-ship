# CANON — горячие правила, читаемые каждым скиллом

Два сквозных правила, к которым обращается почти каждый этап: **slug** (имя директории фичи) и **workflow-нотация** (DSL поведения). Вынесены сюда отдельным маленьким файлом, чтобы скилл грузил их, а не весь README. README остаётся картой и держит остальные (редкочитаемые) протоколы.

## Slug-правило

Имя директории фичи в `.ship/pipeline/{slug}/`:

```
{slug} = {bd-id}-{kebab}
kebab  = 4–6 значимых слов из feature.title, lowercase, через дефис
```

Пример: `bd-2026-0002` + «DB connection reconnect» → `bd-2026-0002-db-connection-reconnect`.

Единое правило во всех скиллах. Survey до создания BusinessDoc живёт в `_intake/`, shape-doc переносит его в `{slug}/`.

## Workflow-нотация

Единый DSL описания поведения во всех артефактах. Имена состояний — из доменного глоссария `CONTEXT.md`, не выдуманные синонимы.

```
состояние --шаг--> состояние                      # переход
[ветка 1, ветка 2]                                # условные ветки
(ветка 1, ветка 2)                                # параллельные ветки
состояние: Тип --шаг--> состояние: Тип            # типизированные состояния (опционально)
{старый workflow} --шаг--> {новый workflow}       # рефакторинг существующего код-пути
```

| Артефакт | Поле | Описывает |
|---|---|---|
| survey | `observed_workflows[].workflow` | код КАК ЕСТЬ |
| bd | `feature.workflow`, `acceptance_criteria[].workflow` | поведение TO-BE; при изменении существующего код-пути — рефакторинг-форма от `observed_workflows` |
| task | `test_scenarios[].workflow` | контракт теста для RED: arrange из `input`, act по шагам, assert ровно `expected_outcome` |
| review | check #2 | тест ассертит конечное состояние `workflow`, не ослабленную версию |
| docs/workflows | тела документов | канон поведения; строки копируются из артефактов, не пересочиняются |

Правила применения:
- Типизированная форма — когда тип состояния уже задан `spec.interface` или `shape.intermediate_structures`; не выдумывать типы ради синтаксиса.
- Рефакторинг-форма — когда фича меняет наблюдаемый код-путь и есть survey: `{имя из observed_workflows} --шаг--> {новый workflow}`. Связывает AS-IS и TO-BE явно; doc-promote по ней видит, какие workflow канона замещаются.
- Поля `workflow` везде опциональны: проза/GWT достаточны для линейных случаев, DSL — для ветвистых.

## Сквозные законы артефактов

Общие для всех скиллов, пишущих JSON-артефакты. Скилл ссылается сюда, не переписывает.

- **Сохранить до отчёта.** Файл записан на диск до того, как скилл рапортует о завершении. JSON только в чат — не результат.
- **Пустой список — `[]`, не опускать.** Каждое поле-список присутствует всегда; `[]` явно означает «проверено, пусто».
- **Выборка через INDEX.** ADR и workflow-доки берутся через `INDEX.md`: фильтр по `Status` + пересечение `Area` с областью работы → грузить тела ТОЛЬКО matched. Не читать `.ship/docs/**/*.md` подряд.
- **Имена состояний — из `CONTEXT.md`.** Доменный глоссарий, не выдуманные синонимы (см. «Workflow-нотация»).

Структурная часть этих законов — **энфорсмент, а не просьба**: PostToolUse-хук `ship-validate.py` проверяет каждый записанный артефакт в `.ship/pipeline/` (обязательные поля, `[]` вместо опущенного списка, `$schema` на месте, инварианты этапа) и возвращает нарушение агенту текстом. Провал = переписать файл, а не «сохранил, поехали». Смысловая часть (осмысленна ли причина, верен ли корень) остаётся на review и человеке — валидатор ловит форму, не халтуру.

## Area-маппинг

Область артефакта по feature-based структуре путей (ADR-001). Едино для adr-promote и doc-promote-internal.

| Путь | Area |
|---|---|
| `src/Projection/...` | `projection` (+ подобласть, напр. `projection/wallet`) |
| `src/Importer/...` | `importer` |
| `src/Api/...` | `api` |
| `src/Reports/...` | `reports` |
| `src/Shared/...` | `shared` |
| структура / несколько фич | `architecture` или `all` |

Неоднозначно — спросить maintainer.
