# Сценарии использования: как гнать spec-ship экономично

Пайплайн полный по умолчанию, но большинство задач не требуют всех этапов. Экономия — не в пропуске работы, а в **переиспользовании канона** (`.ship/docs/adr/` + `.ship/docs/workflows/`): решение или паттерн, промоутнутый один раз, читается вместо повторной трассировки и повторного интервью.

Два канона переиспользуются по-разному:

- **ADR-канон** (`.ship/docs/adr/`) читают почти все этапы — survey, shape-doc, decompose, review (через INDEX, тела только matched по Area). Решения едут в контекст автоматически, отдельного действия не требуют.
- **Workflow-канон** (`.ship/docs/workflows/`, «как система себя ведёт») полноценно переиспользует **survey** (шаг «Собрать контекст», [01-survey](01-survey.md)): тянет `current`-доки по Area как готовые `observed_workflows` и трассирует только отличия. decompose трогает его лишь для fan_out-контракта (порты+DTO), больше никто.

Отсюда ключ к экономике: чтобы переиспользовать **поведенческий** канон паттерна, дай якорь — прогон зайдёт через survey, survey прочитает `current`-доки по Area и не будет трассировать заново. Без якоря survey не запустится, и паттерн-доки никто не подхватит.

Не уверены, какой кейс ваш — спросите прямо в сессии: **`/spec-ship:ask-ship «ваша задача»`** разберёт вход и назовёт команду. Эта страница — развёрнутый разбор кейсов за той подсказкой.

## Быстрый выбор

| Задача | Что запускать | Что пропускается | Почему |
|---|---|---|---|
| Сложная, многослойная, новое решение | полный `/spec-ship:run` (или сначала `roadmap`) | ничего | нужны все гейты — решение дорогое |
| Простая понятная фича | `/spec-ship:run --auto-decompose` | ручной апрув разбивки | всё ROUTINE, шейпить нечего |
| Клон уже сделанного паттерна | `/spec-ship:run … --auto-decompose` **с якорем на эталон** | shape-интервью, LOGIC/CRITICAL гейты | канон уже описал паттерн |
| Точечная дельта к паттерну | `/spec-ship:run` с якорем, дельта в описании | survey-трассировка (канон = база) | меняется только отличие |
| Исследование / «с чего начать» | `/spec-ship:survey` или `/spec-ship:roadmap` | build/review | ещё нечего строить |
| Баг: симптом вместо требования | `/spec-ship:bug-fix` | shape-doc + decompose | целевое поведение выясняется, не шейпится ([09-bug-fix](09-bug-fix.md)) |
| Бамп версии, опечатка | ничего, руками | весь пайплайн | церемония дороже пользы ([process](process.md#когда-spec-ship-не-нужен)) |
| Эпик на несколько фич | `/spec-ship:roadmap` → по фиче `run` | — | планирование над пайплайном ([00-roadmap](00-roadmap.md)) |

Дальше — детали каждого кейса.

## 1. Сложная многослойная задача (новое архитектурное решение)

Новое поведение, задевает несколько слоёв (persistence → logic → API → propagation), решения ещё не приняты.

**Гнать полный цикл, все гейты включены.**

```
/spec-ship:run <описание>; якорь <символ в существующем коде>
```

- **survey** трассирует impact — карта связанных поверхностей, что сломается.
- **shape-doc** интервью — happy/edge/sad, DoD, конфликты с ADR.
- **decompose** режет на вертикальные слайсы, ставит `trust_zone`. LOGIC-слайсы → шейп-сессия; CRITICAL (миграции, деньги, целостность) → только консультация, код пишешь сам.
- **build/review** по каждому слайсу.

Экономить здесь нечем и не нужно: цена ошибки высокая, а решения, которые примешь, промоутятся в ADR/workflows и удешевят **следующие** задачи в этой области. Это инвестиция в канон.

Если задача крупнее одной фичи (дерево вскрывающихся решений) — сперва [`roadmap`](00-roadmap.md): расчертит карту, каждая созревшая фича уйдёт в `run` с обогащённым handoff (решения эпика едут с ней, shape не переспрашивает).

## 2. Простая понятная фича

Скоуп ясен, слоёв мало, архитектурной неоднозначности нет — но фича новая (не клон).

```
/spec-ship:run <описание>; якорь <символ> --auto-decompose
```

- `--auto-decompose` авто-апрувит разбивку, **только если все слайсы ROUTINE** ([08-run](08-run.md), флаги). Появится LOGIC/CRITICAL — прогон сам остановится на апрув: это защита, не помеха.
- shape-интервью пройдёт быстро (специфицировать почти нечего), но апрув спеки оставь ручным — глянуть, что интервью не переусложнило.
- `--auto-shape` добавляй, только если уверен, что открытых вопросов не будет; иначе дешёвый гейт апрува bd не мешает.

Не пиши TaskSpec руками ради «быстрее» — decompose из survey выведет `files_to_change` с причинами точнее, чем из головы.

## 3. Задача, аналогичная уже выполненной (клон паттерна)

Самый частый и самый экономичный кейс. Пример: сделал GraphQL-эндпоинт отчёта rev-share affiliates полным циклом; теперь нужен такой же для CPA affiliates — тот же паттерн, другие source-таблицы.

**Не гони полный цикл. Но и не пропускай survey — именно он переиспользует канон.**

```
/spec-ship:run <описание клона> (клон <эталон>, source-таблицы <...>); якорь <эталонный символ> --auto-decompose
```

Что происходит и почему дёшево:

- **Якорь на эталон обязателен.** С якорем прогон идёт через survey ([08-run](08-run.md), шаг 1). survey прочитает `current` workflow-доки по Area (reports + api) через INDEX — и **переиспользует их как `observed_workflows`**, трассируя только отличия (другие таблицы), а не весь паттерн заново. Это и есть окупаемость промоушена, ради которого ты сохранял канон.
- **shape-интервью почти пустое** — паттерн известен, шейпить нечего.
- **decompose ставит `trust_zone: ROUTINE`, `shape: null`** — нет архитектурной неоднозначности. `--auto-decompose` авто-апрувит.
- **build** — честный Two-Agent TDD: `ship-red` пишет падающие тесты без доступа к `src`, `ship-green` реализует. **review** проверяет против канона.

**Чего НЕ делать:**
- ❌ Полный `run` со всеми гейтами — прогонишь интервью и ручные апрувы впустую.
- ❌ Пропустить survey (запустить без якоря как «greenfield») — тогда **поведенческий канон паттерна никто не подхватит** (ADR-решения дойдут и без survey, а вот workflow-доки — нет), decompose будет выводить файлы из головы. Клон существующего паттерна — это изменение/расширение существующего поведения, у него есть якорь, а не greenfield.
- ❌ Промоутить новый ADR/канон после клона — решение то же, что у эталона. `doc-promote-feature` нужен, только если клон **изменит** паттерн (см. кейс 4).

**Почему не «просто агент со ссылкой на канон»:** за примерно те же токены получаешь честные RED-тесты (агент не может подогнать тест под реализацию — [04-build](04-build.md)) и review против канона. Голый агент этих гарантий не даёт.

## 4. Точечная дельта к существующему паттерну

Клон, но с отличием не только в данных: другая формула reward, другой owner-column, лишний фильтр. Не новый эндпоинт-с-нуля и не чистый клон.

**Канон-док — база, отличие — в spec конкретной задачи.**

```
/spec-ship:run <описание>; якорь <эталон>; дельта: <что именно иначе>
```

- survey подхватит канон паттерна как базу, дельту оттрассирует по коду.
- Дельта локальна → слайс дельты может быть LOGIC (если в отличии есть алгоритмическая неоднозначность), остальное ROUTINE. Прогон сам разведёт: LOGIC-слайс встанет на шейп, ROUTINE поедут автономно ([08-run](08-run.md), правило независимости задач).
- Полный цикл с новым ADR нужен, **только когда дельта = новое архитектурное решение**, которого нет в ADR/workflows. Тогда после мёржа — `doc-promote-feature`, чтобы дельта вошла в канон.

## 5. Исследовательская задача

Нужно знание, а не код: «как сейчас работает X», «с чего начать», «какую БД/протокол выбрать».

Два инструмента, оба останавливаются до кода:

- **`/spec-ship:survey <якорь>`** — если вопрос «как устроен существующий код». Трассирует, отдаёт доказательную карту. Артефакт живёт и переиспользуется: следующий `run` по этой области стартует с готового survey. Можно сразу закрепить в канон через [`doc-backfill`](07-doc-promote.md) — описать паттерн один раз, чтобы будущие фичи стартовали не с нуля.
- **`/spec-ship:roadmap <размытая идея>`** — если вопрос «что делать и в каком порядке» на несколько фич. Чертит карту решений, резолвит тикеты-вопросы по одному ([00-roadmap](00-roadmap.md)). Тикеты типов `survey`/`prototype`/`grilling` — это и есть исследование, оформленное как разблокирующие решения.

Не запускай `run`, пока не знаешь, что строить — прогонишь shape-интервью впустую.

## 6. Backfill: описать существующий паттерн заранее

Особый профилактический кейс. Область ещё не проходила пайплайн, но по ней скоро пойдут фичи. Опиши эталон **до** первой фичи:

```
/spec-ship:survey <эталонный символ>
/spec-ship:doc-backfill   # survey → workflow-канон, без MR-гейта
```

Тогда первая же фича в области (кейс 2/3) стартует с готового канона, а не с холодной трассировки. Разовая инвестиция, окупается со второй задачи в области.

---

## Общий принцип экономии

1. **Поведенческий (workflow) канон подхватывает survey → давай якорь**, если задача касается существующего кода. ADR-решения доходят и без survey (их читают shape-doc/decompose/review), а вот паттерн-доки `.ship/docs/workflows/` — только через survey.
2. **Флаги снимают только низкорисковые гейты** (`--auto-decompose` — при всех ROUTINE; `--auto-shape` — при 0 blocking). Высокорисковые (LOGIC-шейп, CRITICAL, эскалации, review ESCALATE) не снимаются никогда — прогон сам остановится, где решение принципиально твоё.
3. **Промоутить в канон — только новое.** То же решение повторно в ADR/workflows не идёт. Промоушен нужен, когда появилось решение или паттерн, которых в каноне ещё нет.
4. **Сомневаешься, гейт или нет → гейт.** Дешевле лишний апрув, чем неверная спека, замороженная в тумане.

→ Когда spec-ship вообще не нужен — [process](process.md#когда-spec-ship-не-нужен).
