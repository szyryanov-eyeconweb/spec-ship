# ReviewReport — поля артефакта

Файл: `.ship/pipeline/{slug}/review-<task-id>.json`

ReviewReport — это машинный вердикт независимого ревью готового билда против его задачи, бизнес-спеки и принятых решений. Build уже делал самопроверку, но проверять себя — конфликт интересов; review смотрит на результат отдельным чеклистом фиксированных проверок и решает, можно ли открывать merge request.

## `id`, `build_report_id`, `task_spec_id`, `created_at`

Ссылки на проверяемые артефакты.

## `verdict`

Один из трёх исходов, определяющий, что происходит дальше:

- `APPROVED` — все проверки прошли, `mr_ready: true`, можно открывать merge request.
- `NEEDS_WORK` — найдены проблемы, но их может исправить сам агент без участия разработчика. Список проблем — в `issues[]`, дальше следует повторная попытка build и повторное review.
- `ESCALATE` — фундаментальный конфликт со спекой, проблема безопасности или архитектурное нарушение. Требует разработчика, и в отчёт уже собран весь нужный контекст.

## `checklist` — шесть фиксированных проверок

Все шесть ключей присутствуют в каждом отчёте всегда — даже если проверка неприменима к этой задаче, она отмечается явным `pass: true` с пометкой `n/a`, а не пропускается. У каждого ключа — `pass` (прошла или нет) и `notes` (при провале — конкретный `файл:строка`, а не общая формулировка).

1. **`spec_coverage`** — весь заявленный интерфейс реализован, недокументированных полей/эндпоинтов нет; точные значения из `data[]` задачи присутствуют в коде буквально, без тихого округления или «нормализации». Если данные лежали крупным файлом (`value_ref`), эта проверка сверяет контрольную сумму файла с тем, что записано в артефакте, а не сверяет содержимое глазами.
2. **`test_scenarios_covered`** — на каждый сценарий из задачи есть тест через публичный интерфейс; тест ассертит именно результат поведения, а не то, что внутренний метод был вызван N раз (исключение — реальные внешние эффекты вроде платежа или отправки события, там проверка факта вызова легитимна). Тест написан на заявленном `test_seam`, не глубже и не через обход границы моками.
3. **`adr_violations`** — реализация не нарушает ни одного связанного ADR; новые кандидаты-решения не противоречат существующим; ни одна ссылка не указывает на устаревший (Expired) ADR.
4. **`regressions`** — вызывающие изменённый код не сломаны, новых падений тестов нет.
5. **`performance`** — если в Definition of Done фичи были требования к latency/throughput, они адресованы реализацией.
6. **`regression_guard`** — применяется только к задачам из bug-fix (`n/a` на обычных фичах). Проверяет, что репро-тест бага был красным до фикса и остался в наборе тестов навсегда, что фикс лежит в общей точке для всех задетых вызывающих (а не в одном пути из исходного тикета), что каждый затронутый тем же корнем сосед либо покрыт этим же билдом, либо получил свою задачу, и что чистка испорченных данных идёт отдельной задачей, а не смешана с фиксом кода.

## `issues[]`

Список конкретных проблем при `NEEDS_WORK` или `ESCALATE`; пуст для `APPROVED`. Каждая запись — `severity` (`blocking` или `warning`), `location` (`файл:строка`) и `description`.

## `escalation`

`null` для всех вердиктов, кроме `ESCALATE`. При эскалации — `reason` (в чём суть конфликта) и `recommended_action` (что предлагается сделать дальше). Так разработчик получает не просто «что-то не так», а готовую отправную точку для решения.

## `mr_ready`

Единственный флаг, который реально открывает или блокирует merge request. `true` **только** тогда, когда `verdict == APPROVED` **и** нет ни одного незакрытого TestUpdateTicket, ни одного незакрытого тикета конфликта с ADR. То есть даже полностью чистый чеклист не откроет MR, если рядом висит нерешённый тикет, ожидающий человека.
