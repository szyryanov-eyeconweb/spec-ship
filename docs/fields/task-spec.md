# TaskSpec — поля артефакта

Файл: `.ship/pipeline/{slug}/task-<NNNN>-<NN>.json`

TaskSpec — это одна маленькая самодостаточная задача, на которые decompose режет фичу (или которую создаёт bug-fix для починки бага). У задачи есть контракт (что на входе, что на выходе), назначенная зона доверия и, если нужно, набор тестовых сценариев. Это последний артефакт, который видят сабагенты build (`ship-red` и `ship-green`) — они работают изолированно и не видят BusinessDoc целиком, поэтому TaskSpec обязан содержать всё нужное сам по себе.

## `id`, `created_at`

`id` вида `task-0042-03` — используется в BuildReport, ReviewReport и в TestUpdateTicket как ссылка на задачу.

## `business_doc_id` и `diagnosis_id`

Ровно одно из двух полей заполнено, второе — `null`. Это явно показывает происхождение задачи: фича приходит из BusinessDoc (`business_doc_id` заполнен), баг — из Diagnosis (`diagnosis_id` заполнен). Так `build` и `review` не отличают одно от другого технически — механика одна и та же, но происхождение всегда прослеживается.

## `title`

Короткий заголовок в повелительном наклонении («Добавить фильтр по меткам», не «Фильтр по меткам добавлен»).

## `trust_zone` — сколько свободы дать агенту

**Зачем это главное поле артефакта:** переименовать поле в DTO и написать миграцию, двигающую деньги, — работы принципиально разного риска, и решение «дать агенту делать это самостоятельно» должно быть явным и проверяемым, а не подразумеваемым.

- `ROUTINE` — описания и интерфейса достаточно, чтобы написать код без угадывания. Сабагенты `ship-red`/`ship-green` работают полностью автономно.
- `LOGIC` — нужны нетривиальные решения (промежуточные структуры, порядок обработки, алгоритм). Перед кодом обязательна шейп-сессия с разработчиком; без апрувнутого `shape` `ship-green` не запустится.
- `CRITICAL` — целостность данных, безопасность, миграции. Сабагенты не вызываются вовсе; код пишет разработчик, агент — только консультант.

`trust_zone` ставится decompose (или bug-fix) один раз и дальше пробрасывается без изменений в BuildReport и ReviewReport — это гарантирует, что риск-профиль задачи не «размывается» по мере прохождения пайплайна.

## `spec` — контракт задачи

- `description` — что строить, поведение целиком, от входа до выхода.
- `interface.input` / `interface.output` — карта имя поля → тип. Это буквальный контракт: review потом проверяет, что реализован весь интерфейс и не появилось недокументированных полей сверх.
- `test_seam` — на каком уровне `ship-red` будет писать тесты. Заполняется явно, чтобы `ship-red` не гадал (неявный seam иначе всплывает эскалацией уже в середине build):
  - `level` — `unit` (тест бизнес-логики изнутри), `functional` (сценарий на всю фичу) или `use-case-harness` (через публичный вход, но не через полный HTTP-стек).
  - `entry` — конкретная точка входа теста: класс/метод/эндпоинт, тот же, что в `spec.interface`.
  - `existing` — использует ли тест уже существующую в проекте границу тестирования (предпочтительно) или заводит новую.
  - `prior_art` — путь к похожему существующему тесту, если `existing: true`. Обязателен в этом случае: «existing» без указания, на что оно похоже, не считается.
  - `null` целиком, если у слайса `test_scenarios: []` — тестировать нечего, слайс покрыт функциональным набором фичи на другом, «слайсе-носителе».
- `files_to_change[]` / `files_read_only[]` — списки файлов. Если был survey, эти списки выводятся из его `files_evidence`, а не придумываются заново. Разработчик проверяет на апруве, что оба списка не смешивают файлы из несвязанных областей.

## `shape` — план для LOGIC-задач

`null` для `ROUTINE` и `CRITICAL`. Для `LOGIC` — обязателен, и решает конкретную проблему: агент не должен изобретать нетривиальный алгоритм в одиночку, а разработчик не должен придумывать весь план с нуля, если decompose уже видит контуры решения.

- `status` — `proposal` (decompose набросал скелет с открытыми вопросами) или `approved` (разработчик на шейп-сессии подтвердил план). **`ship-green` не запустится, пока `status` не станет `approved`** — это жёсткое условие, не пожелание.
- `approach` — выбранный алгоритмический путь.
- `intermediate_structures[]` — промежуточные структуры данных с именем (`name`), из чего они выводятся (`derived_from`), кто их потребляет (`consumed_by`) и какие инварианты они несут (`invariants` — то, что снимает необходимость перепроверки этих данных ниже по потоку).
- `ordering_rules[]` — правила порядка обработки, батчинга, агрегации.
- `open_for_developer[]` — то, что decompose сознательно оставил нерешённым для обсуждения на шейп-сессии. Это повестка встречи, а не недоработка.
- `approved_by`, `approved_at` — кто и когда подтвердил план.

## `fan_out` — параллельная сборка по слоям (необязательно)

`null` по умолчанию — обычная последовательная сборка. Заполняется, только когда задача делится на независимые по файлам слои-роли (`entry` / `application` / `contract-impl`) с заранее известным контрактом между ними — тогда `build` может собирать слои параллельно, экономя время, а не токены.

- `enabled` — включён ли режим.
- `contract_paths[]` — пути портов и DTO; фиксируются первой фазой сборки, дальше слои их только читают.
- `shared_paths[]` — общая инфраструктура (DI, реестр, схема), тоже фиксируется заранее; `[]`, если общей земли нет.
- `layers[]` — список слоёв, у каждого `role` и свой `files_to_change`.

Разработчику важно проверять на этапе апрува три вещи (в коде это уже проверяет валидатор): пути слоёв не пересекаются друг с другом, и ни один путь слоя не пересекает `contract_paths` или `shared_paths`. Нарушение любого из этих условий означает, что параллельность объявлена ошибочно и сборка пойдёт обычным последовательным путём. Полная механика — `skills/FAN-OUT.md`.

## `data[]` — точные значения для этого слайса

Подмножество `data[]` из BusinessDoc, нужное именно тестам этой задачи — скопированное **значением**, с сохранением того же `id` (`d-N`), а не ссылкой: сабагенты работают в изоляции и BusinessDoc целиком не видят. Крупные значения (`value_ref`) копируются как дескриптор, включая `checksum` — сам файл не инлайнится и не переносится копией.

## `test_scenarios[]` — что именно проверяют тесты

`[]`, если слайс не несёт собственной логики (тонкий адаптер, чистая схема) — тогда его покрывает функциональный набор фичи на другом слайсе, и плодить тест «для галочки на каждый слайс» не нужно.

- `id` (`ts-1`), `scenario` (`happy` / `edge` / `sad`), `description`.
- `workflow` — необязательная стрелочная строка (`состояние --шаг--> конечное состояние`), для ветвистых критериев берётся напрямую из `acceptance_criteria[].workflow` BusinessDoc: каждая ветка условия превращается в отдельный сценарий с явным исходом.
- `input` / `expected_outcome` — обязательны, если заполнен `workflow`. Именно `expected_outcome` (не более слабая формулировка) проверяет review: тест обязан ассертить ровно этот исход, включая тип исключения для `sad`-сценариев.

Для задачи из bug-fix здесь всегда присутствует репро-сценарий бага — он остаётся в наборе тестов навсегда как регрессионный сторож, даже после исправления.

## `dependencies`

`depends_on[]` — какие задачи должны быть готовы раньше этой. `blocks[]` — какие задачи ждут эту. Используется для порядка сборки и для того, чтобы независимые задачи собирались параллельно, пока заблокированная ждёт решения разработчика.

## `adr_refs[]`

Принятые решения (ADR), релевантные этой конкретной задаче — отфильтрованные ещё на уровне survey/BusinessDoc, здесь просто перенесённые. `build` резолвит их через `INDEX.md` и учитывает при реализации; `review` проверяет, что ни одно из них не нарушено.

## `validation`

- `business_doc_coverage[]` — какие именно `acceptance_criteria` (по id `ac-N`) покрывает эта задача. Для задачи из bug-fix — всегда `[]`, потому что покрытие там сверяется не с критериями приёмки, а с `defect.expected` из Diagnosis.
- `risk` — `low` / `medium` / `high`, субъективная оценка decompose.
- `risk_reason` — почему именно такой уровень риска, если он не `low`.
