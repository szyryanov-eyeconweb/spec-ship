# BuildReport — поля артефакта

Файл: `.ship/pipeline/{slug}/build-<task-id>.json`

BuildReport — итог работы шага build над одной задачей: что сделали RED и GREEN, сколько итераций потребовалось, какие файлы изменились, и самопроверка агента перед тем, как отдать результат на независимое ревью. Это не отчёт «для галочки» — review читает именно эти поля вместо того, чтобы заново перепроверять весь процесс сборки.

## `id`, `task_spec_id`, `trust_zone`, `created_at`

`trust_zone` пробрасывается сюда без изменений из TaskSpec — так на этапе review виден риск-профиль задачи, не нужно открывать TaskSpec заново.

## `fan_out`

`null`, если задача собиралась обычным последовательным путём. Если использовалась параллельная сборка по слоям — здесь фиксируется исход по каждому слою: `layers[]` (роль, статус, путь к git worktree, в котором слой собирался), `shared_written` (общая инфраструктура была записана), `merged` (слои успешно слиты воедино). Статус слоя — один из `done`, `escalated`, `conflict`, `immature-contract` (контракт между слоями оказался незрелым, пришлось остановиться и дошейпить) или `out-of-bounds` (слой попытался записать файл за пределами своей зоны — это ловит инфраструктура изоляции worktree, а не сам агент).

## `tdd` — что сделали RED и GREEN

- `agent_red.status` — `"done"`, если тесты написаны и подтверждены красными.
- `agent_red.tests_written` — сколько тестов написано.
- `agent_red.test_files[]` — какие файлы созданы.
- `agent_red.all_red_confirmed` — явное подтверждение, что все новые тесты действительно упали до реализации. Без этого подтверждения тесты нельзя считать честными: тест, который проходит и без кода, проверяет форму, а не поведение.
- `agent_green.status` — `done` (все тесты зелёные), `escalated` (не уложился в лимит итераций, задача уходит на переклассификацию в LOGIC) или `conflict` (реализация требует изменить существующий тест — вместо этого создаётся TestUpdateTicket, и GREEN останавливается).
- `agent_green.iterations` — сколько итераций потребовалось (лимит фиксирован в самом сабагенте).
- `agent_green.files_changed[]` — какие файлы изменены. **Важно:** валидатор схемы (`ship-validate.py`) требует список `files_changed` на верхнем уровне всего артефакта, а не только внутри `tdd.agent_green` — при заполнении отчёта стоит продублировать этот список на верхний уровень, иначе автоматическая проверка формы артефакта не пройдёт.
- `agent_green.all_green_confirmed` — подтверждение, что весь набор тестов (не только новые) прошёл, то есть регрессий не внесено.
- `agent_green.conflict` — заполняется только при `status: conflict`: `test_id` и `reason`, почему тест не мог остаться прежним.

## `escalation`

`null`, если сборка прошла без эскалации. Иначе — `reason` (`green_iterations_exceeded` или `test_spec_conflict`), `escalated_to` (`"LOGIC"` — задача переквалифицируется, дальше решение проектирует разработчик), `details` и, если применимо, ссылка на созданный `test_update_ticket`.

## `adr_entries[]`

Список id кандидатов в архитектурные решения (`ADREntry`), рождённых во время этой сборки — или `[]`, если по ходу реализации не было принято решений, достаточно значимых, чтобы фиксировать их в каноне.

## `self_review` — самопроверка агента

- `spec_coverage` — весь заявленный интерфейс реализован.
- `adr_violations[]` — список нарушенных ADR; **обязан быть `[]`**. Если здесь появляется хоть одна запись, это автоматически блокирует `mr_ready` на следующем шаге (review) — самопроверка не заменяет review, но если агент сам знает о нарушении, оно не должно потеряться.
- `notes` — неочевидные заметки о реализации (например, для CRITICAL-задачи здесь явно отмечается «CRITICAL: реализовано разработчиком», чтобы review не искал автозаписи агента там, где их не было и не должно быть).

**Зачем нужна именно самопроверка, если дальше всё равно есть review:** это не замена независимой проверке (агент, проверяющий сам себя, — конфликт интересов), а фильтр очевидных проблем до того, как задача попадёт к отдельному ревьюеру. Финальное решение всё равно принимает review по собственному чеклисту.
