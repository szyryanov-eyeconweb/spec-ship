# ADR (канон решений) — структура документа

Файл: `.ship/docs/adr/ADR-<NNN>-<kebab>.md`, регистрируется строкой в `.ship/docs/adr/INDEX.md`

Это не JSON-артефакт пайплайна, а конечная точка знания: канонический markdown-документ, в который `adr-promote` превращает одобренный кандидат ADREntry. Здесь решение перестаёт быть «результатом одной задачи» и становится частью правил проекта — его будут учитывать все последующие фичи в той же области.

## Заголовок и шапка

```markdown
# ADR-<NNN>: <Заголовок решения>

**Status:** Accepted
**Date:** <ISO-date>
**Author:** <maintainer>
**BD:** <business_doc_id>
**Task:** <task_spec_id>
```

- `NNN` — сквозной номер, `максимальный существующий + 1`. Нумерация никогда не переиспользуется, даже для устаревших (Expired) ADR — так ссылка на конкретный номер остаётся однозначной навсегда.
- `Status` — на момент создания всегда `Accepted`. Статус может позже смениться на `Expired`, если решение устарело; тогда ссылки на него в новых артефактах должны считаться конфликтом, требующим разрешения (см. протокол ADR-CONFLICT).
- `BD` / `Task` — откуда взялось решение: из какого BusinessDoc и какой конкретной задачи. Это трассируемость: через полгода можно понять, в контексте какой фичи это было решено.

## `## Context`

Зачем это решение вообще понадобилось — какая проблема или ограничение к нему привели. Переносится из поля `context` исходного ADREntry.

## `## Decision`

Само решение — что именно было выбрано. Из поля `decision` ADREntry; внутри текста могут быть inline-ссылки на конкретные файлы (`files_ref` из ADREntry).

## `## Consequences`

Список следствий: что решение даёт и чем расплачивается. Раздел включается, только если в исходном ADREntry реально есть такие записи — пустые разделы не создаются заранее «на будущее».

## `## Considered Options`

Какие альтернативы рассматривались и почему отклонены. Это главная защита от повторного пересмотра решения без новых аргументов: следующий разработчик видит, что альтернатива уже была на столе.

## Область (Area) и запись в INDEX

Область решения выводится из затронутых файлов по единому Area-маппингу (`skills/CANON.md`) — то же самое отображение путей в область, которым пользуется и `doc-promote` для workflow-документов. В `INDEX.md` добавляется строка:

```
| <NNN> | Accepted | <area> | <decision кратко> | — |
```

**Зачем именно так устроена выборка:** ни один скилл пайплайна не читает все ADR подряд — только `INDEX.md`, отфильтрованный по статусу `Accepted` и пересечению области с текущей фичей, и лишь затем открывает тела только совпавших записей. Поэтому даже сотня накопленных решений в проекте не утяжеляет контекст новой фичи — в него попадает один индекс и два-три релевантных документа.
