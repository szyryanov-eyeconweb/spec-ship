# Поля артефактов spec-ship

Пайплайн spec-ship на каждом шаге читает и пишет JSON-артефакты (и два вида markdown-документов канона). Эти файлы — не просто промежуточный вывод для отчётности: следующий шаг читает конкретные поля предыдущего и принимает по ним решения. Здесь собрано подробное описание каждого поля — для чего оно существует, кто его заполняет, кто и как читает дальше, что будет, если его не заполнить.

Это справочник для человека. Формальная схема (JSON-структура, которую обязан соблюдать агент) лежит в `skills/<skill>/SCHEMA.md` — тут то же самое, но развёрнуто и с объяснением смысла.

## Как артефакты связаны друг с другом

Каждый артефакт ссылается на предыдущий по id и почти всегда переносит вперёд то, что важно последующим шагам, а не то, что было интересно на своём шаге. Общая цепочка для фичи:

```
Survey (опционально)
  → BusinessDoc (замороженная бизнес-спека)
    → TaskSpec × N (по одному на вертикальный слайс)
      → BuildReport (реализация + тесты)
        → ADREntry (опционально — кандидат в решение)
      → ReviewReport (вердикт: можно ли открывать MR)
        → [после мёржа] ADR-NNN.md (канон решений)
        → [после мёржа] workflow-документ (канон поведения)
```

Для входа через баг (`bug-fix`) цепочка короче: Survey обязателен, вместо BusinessDoc — Diagnosis, вместо N слайсов обычно один TaskSpec. Дальше — тот же build/review.

Для крупных эпиков цепочка растёт на уровень выше: `roadmap` создаёт `MAP.json` и тикеты, и уже из закрытого тикета конкретная фича передаётся в `run` (обычный пайплайн выше) с обогащённым контекстом.

## Сквозные правила, общие для всех артефактов

Прежде чем читать конкретные поля, полезно знать три правила, которые соблюдаются везде одинаково (подробно — `skills/CANON.md`):

- **Пустой список — это `[]`, а не отсутствие поля.** Если поле-список пусто, оно всё равно присутствует в JSON со значением `[]`. Это значит «агент проверил и ничего не нашёл», а не «агент забыл проверить».
- **Файл сохраняется на диск до того, как агент отчитается о завершении шага.** Артефакт, который существует только в переписке, не считается результатом.
- **ADR и workflow-документы читаются через свой `INDEX.md`, а не все подряд.** У обоих канонов (`.ship/docs/adr/` и `.ship/docs/workflows/`) есть общий индекс-файл со статусами и областями (Area). Каждый шаг сначала смотрит в индекс, отбирает только пересекающиеся по области и актуальные по статусу записи, и лишь затем открывает конкретные файлы. Это единственный способ, которым канон остаётся дешёвым: сто принятых решений в проекте не означают, что каждая фича будет читать все сто.

## Зачем вообще так подробно описывать поля

Каждое поле в этих артефактах добавлено не для строгости ради строгости, а потому что решает конкретную проблему, которая на практике случается при разработке с участием AI-агентов: агент придумывает не то, что имелось в виду; тест подгоняется под уже написанный код; правка ломает соседний код-путь, про который никто не подумал; решение, принятое в чате, забывается через полгода. У каждого файла с описанием поля есть раздел «зачем» — он объясняет именно эту связь.
