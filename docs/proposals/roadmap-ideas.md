# Идеи развития spec-ship

Бэклог идей за пределами Pocock-плана (тот — `borrow-from-pocock.md`).
Дата: 2026-08-16.

## 1. Флаг `skip_tests` — убрать TDD-оверхед где не нужен — 🎯 РЕШЕНО делать

**Проблема.** build всегда гонит Two-Agent TDD (RED→GREEN) для ROUTINE. Для
glue-кода, скриптов, конфигов написание тестов = чистый оверхед: поведение
тривиально, регресс дёшев.

**Обсуждённые варианты (история решения):**
- Полная ось `build_strategy` (tdd / contract-first / code-only / test-after) +
  матрица trust_zone — ОТВЕРГНУТО: комбинаторный взрыв (3×2×4=24 ветки),
  `contract-first` дублирует fan_out Phase A, `test-after` YAGNI для PHP/DDD.
  Из 4 стратегий реально нужна одна (code-only).
- Выбор агентом по эвристике — ОТВЕРГНУТО: агент склонен к меньшей работе →
  code-only везде → потеря главной ценности spec-ship, непредсказуемость.

**Решение — минимальное (ponytail):**
- `skip_tests`: bool в TaskSpec, дефолт `false`.
- `false` → сегодняшний build по trust_zone. **Ноль изменений поведения** —
  предсказуемость 100% сохранена (fail-closed дефолт).
- `true` → GREEN пишет код без RED-барьера.
- Задаёт **человек** при decompose. Флаг `/spec-ship:run --skip-tests` двигает
  дефолт прогона; явное значение в TaskSpec сильнее флага.

**Гейт доверия (критично — иначе дыра в сердце spec-ship):**
- ROUTINE → `skip_tests: true` свободно.
- LOGIC / CRITICAL → `skip_tests: true` требует `strategy_override_reason` в
  артефакте + второе подтверждение. Разрешено, но осознанно и зафиксировано.
- `ship-guard.sh` должен быть strategy-aware: не пускать GREEN писать без
  тестов на задачу, где `skip_tests: false` (иначе агент обойдёт барьер).

**Затрагивает:** схема TaskSpec (+поле), decompose (выбор + override-гейт),
build (1 ветка), ship-guard.sh (strategy-aware), review check #2 (адаптация
под skip_tests), run (флаг), README/03-decompose/04-build.

**Расширяемость:** если позже реально понадобятся contract-first/test-after —
`skip_tests` (bool) превращается в enum. НЕ сейчас (YAGNI).

## 2. Идеи от коллег (Egor, Stanislav) — валидируют канон, вскрывают 3 пробела

Контекст: Egor — цикл «лог→чистка→скилл→повтор» + тотальное логгирование.
Stanislav — командный md-knowledgebase «Вася уже сделал так, ты не учёл».
Обе идеи на 95% уже покрыты каноном spec-ship (ADR + workflow-доки + INDEX +
детерминированный промоушен). Не брать: «логгируй каждый чих» в CLAUDE.md —
противоречит принципу «лог = артефакт, не транскрипт». Вскрытые пробелы:

### 2a. `postmortem` — петля обучения на провалах
Причина `NEEDS_WORK`/`ESCALATE`/отката живёт в одном ReviewReport и умирает.
Скилл извлекает анти-паттерн → канон `.ship/docs/pitfalls/` (симметрично
ADR/workflow, выборка по Area). Следующая фича области читает: «здесь уже
спотыкались на X». Кейсы из практики: DAMA extension не зарегистрирован,
test-cache stale metadata, linter Decimal-rollback. *Ценность высокая,
механика зеркалит промоушен.*

### 2b. Проактивный `prior-art` в shape-doc
shape-doc грузит ADR по Area реактивно (конфликт-детект). Добавить проактивный
вывод: «в этой области приняты решения A, B; похожая фича делалась так — учти».
Не блокирует, подсвечивает. *Дёшево, ценно в команде.*

## 3. Мой топ идей (не обсуждались детально)

- **`ship-doctor`** — health-check среды перед build: миграции main+test, кэш,
  DAMA-extension, хуки зарегистрированы, gitignored artifacts. Ловит класс
  инфра-ошибок ДО билда. *Средняя стоимость.*
- **`survey` инкрементальный** — при наличии workflow-дока трассировать
  дифференциально (что изменилось), не с нуля.
- **`spec-lint`** — статический анализ артефактов (DoD без метрики, data-дрейф
  bd↔task, непокрытые ac, циклы depends_on, seam без prior_art). Ложится на
  ship-guard PreToolUse-паттерн.
- **`parallel-run`** — SprintManifest в проде: граф зависимостей + детект
  конфликтов файлов + worktree-изоляция волн. Теория готова в памяти проекта
  (batch-conveyor-sprint-pipeline). roadmap → parallel-run. *Высокая стоимость.*
- **data-слой валидация в CI** — точные значения bd физически в коде; тихо
  изменённая константа = красный CI (кейс linter-type-rollback).

## 4. Баланс точность × скорость × токены

Оптимизации под тройную ось. **Сквозной инвариант (иначе выигрыш съедается
непредсказуемостью):** все адаптивные решения — из УЖЕ существующих полей
(`validation.risk`, `trust_zone`, prior_art, размер diff), детерминированы,
замораживаются в артефакте, апрувятся человеком. Ноль эвристик агента на лету.
Точность не срезается — внимание перераспределяется на рисковое.

### 4a. Модель-по-роли (матрица) — 🎯 главный рычаг токенов
skills/README заявляет «рассуждающая где мышление, исполнительная где
исполнение», но выбор модели зашит грубо. Явная матрица модель×(trust_zone,
risk, роль): RED/GREEN на ROUTINE low → haiku; shape LOGIC → opus; review high
→ opus, low → haiku. Токены ↑↑↑, скорость ↑↑, точность = (тяжёлое остаётся на
тяжёлой). Двигает все три.

### 4b. Общий контекст-пакет прогона — убрать N-кратное чтение
В `run` каждый build-сабагент читает CONTEXT.md + matched ADR + похожие тесты
заново, изолированно. N задач = N-кратный оверхед. Собрать контекст-пакет один
раз, инжектить в каждого сабагента готовым блоком. Токены ↑↑↑, скорость ↑↑,
точность ↑ (сабагенты не расходятся в контексте). Прямая экономия на
fan-out/multi-task.

### 4c. Adaptive gating по risk — гейты по риску, не по типу
`validation.risk` уже в TaskSpec, но не маршрутизирует. risk low + маленький
diff + high prior-art → лёгкий трек (меньше проверок, дешевле модель,
авто-апрув); risk high → полный ритуал. Точность ↑ (фокус на рисковом),
скорость ↑↑, токены ↑↑. Поле есть — связать с маршрутизацией.

### 4d. Adversarial verify только для high-risk
Двухосевое review + N скептиков (из Pocock-плана) — дорого. Применять ТОЛЬКО к
`risk: high`. Low — одна проверка. Точность ↑↑ на критичном при контролируемой
цене.

### 4e. `precheck` перед RED — дешёвый фильтр нетестируемого
RED садится, упирается в `blocked: no_seam`, эскалирует — токены на тупик.
Дешёвый precheck (haiku): «тестируем ли сценарий через seam?» до полной
RED-фазы. Ловит тупик за ~1/10 токенов. Токены ↑, скорость ↑.

### 4f. Diff-scoped review
review читает весь build; менялся только diff. Скармливать только изменённое +
прямые соседи (survey даёт связанные группы). Токены ↑↑, скорость ↑, точность =
(соседи из survey не теряются).

### 4g. Early-exit на нулях
0 конфликтов ADR / 0 TEST-UPDATE → пропустить под-протоколы целиком, не гонять
«на всякий» (barrier-pattern). Токены/скорость ↑ на чистых фичах (большинство).

**Ставка (мультипликативный эффект, все три оси):** 4a + 4b + 4c. Дешёвая
модель × меньше повторного чтения × меньше гейтов на рутине — основная доля
токенов на ROUTINE-heavy прогоне, не хвост. Все три переиспользуют
существующие поля.
