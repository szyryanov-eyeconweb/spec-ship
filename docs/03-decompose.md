# Шаг 1. Decompose — нарезка на задачи и зоны доверия

![Decompose: шинкуем фичу на задачи](assets/1-decompose.png)

```
/spec-ship:decompose
```

## Что это

Decompose читает апрувнутый BusinessDoc и режет фичу на **TaskSpec** — маленькие самодостаточные задачи. Каждой задаче назначается зона доверия: сколько свободы дать агенту. После сохранения задач BusinessDoc замораживается окончательно.

## Зачем

Две причины. Первая — размер: агент надёжно делает маленькие задачи с ясным контрактом и плохо — большие размытые. Вторая — риск: переименовать поле в DTO и написать миграцию денег — работы разного веса, и доверять их агенту одинаково — ошибка. Зона доверия делает это различие явным и проверяемым.

## Что на входе

- Апрувнутый `bd-*.json` (если остались blocking-вопросы без ответа — стоп, сначала дорешать)
- Survey, если был — списки файлов берутся из него доказательно

## Как проходит

1. **Вертикальные слайсы.** Фича режется не по слоям («сначала вся БД, потом весь API»), а вертикально: каждая задача проходит все нужные слои и независимо собирается. Тонкие слайсы лучше толстых. Каждый слайс покрывает минимум один критерий приёмки. Слайс — единица **сборки**, но не единица тестирования: тесты идут на фичу, не на слайс (см. п.3).
2. **Зона доверия** для каждой задачи:

   | Зона | Признак | Что происходит дальше |
   |---|---|---|
   | `ROUTINE` | описания и интерфейса достаточно, чтобы написать код без угадывания | агенты RED/GREEN делают автономно |
   | `LOGIC` | нужны нетривиальные решения: промежуточные структуры, порядок обработки, алгоритм | в TaskSpec кладётся скелет плана (`shape`) с вопросами для вас; перед кодом — шейп-сессия |
   | `CRITICAL` | целостность данных, безопасность, миграции | агенты не запускаются; код пишете вы, агент консультирует |

3. **Тесты — на фичу, не на слайс.** Фича — одна поведенческая единица; покрывать её на каждой внутренней границе слайсов = дублирование. Два уровня, только они:
   - **Функциональный (на фичу)** — один набор сценариев на всю фичу, выведенный из критериев приёмки целиком. Живёт на слайсе внешнего входа (API/эндпоинт/публичный сервис).
   - **Unit (на бизнес-логику)** — только там, где слайс несёт нетривиальную доменную логику (на практике `LOGIC`); проверяет алгоритм/инварианты изнутри, не повторяя функциональный контракт.

   Слайс без своей логики (schema-only, тонкий адаптер, проводка) собственных тестов НЕ несёт (`test_scenarios: []`) — он покрыт функциональным набором фичи. Не плодить тесты формы ради «покрытия каждого слайса».
4. **Test seam** — уровень, на котором RED тестирует, для слайса со сценариями. Не отдаётся на угад RED (иначе всплывает эскалацией в середине билда). Три правила: существующий seam предпочтительнее нового (смотрим, как уже тестируется соседний код по survey и `tests/`); брать высший разумный уровень (тестировать с края — use-case harness / API — а не глубоко внутри); функциональный seam — один на фичу, unit — по одному на LOGIC-слайс. Пишется в `spec.test_seam` (тип + точка входа), RED следует ему как контракту; слайс без сценариев → `test_seam: null`. Нет разумного seam → сигнал `LOGIC` (дошейп с вами), а не догадка.
5. **Сценарии тестов.** Слайс-носитель получает `test_scenarios` — что проверить: happy, edge, sad. Для ветвистых критериев сценарии выводятся из workflow-строки BusinessDoc: каждая ветка — отдельный сценарий с явным исходом. Точные значения из `data` BusinessDoc копируются в задачу — сабагенты работают изолированно и самого BusinessDoc не видят.
6. **Проверка конфликтов с тестами.** Если новая спека противоречит существующему тесту — тест не правится втихую: создаётся отдельный тикет TestUpdateTicket, который должен явно разрешить человек.
7. **Валидация покрытия.** Каждый критерий приёмки покрыт функциональным сценарием (в наборе на фичу), а не просто задет каким-то слайсом; ровно один слайс несёт функциональный набор; нет циклических зависимостей между задачами.
8. **Ваш апрув.** Агент показывает разбивку (название, зона, зависимости) — сохраняет только после вашего «ок». Затем BusinessDoc получает статус `frozen`.

![Матрица доверия: кто на самом деле будет писать код](assets/trust-zone.png)

## Что получится

- `task-*.json` (×N) — у каждой задачи: описание, интерфейс (вход/выход), список файлов «можно менять» / «только читать», зависимости, зона доверия, для LOGIC — скелет плана с пунктами «решить с разработчиком». Тесты — на слайсе-носителе: test seam + сценарии (функц. набор фичи или unit на логику); слайс без своих тестов — `test_scenarios: []`, `test_seam: null`
- `tu-*.json` — тикеты на конфликтующие тесты, если нашлись

## Что от вас потребуется

- Апрув разбивки: адекватны ли слайсы, правильно ли расставлены зоны доверия
- Особенно проверьте зоны: ROUTINE с спрятанной сложностью вернётся эскалацией, а LOGIC из чистой рутины — лишней сессией

## Типичные ошибки, от которых защищает

- задача-монстр через все домены — запрещены смешанные файлы из несвязанных областей
- критерий приёмки, который никто не реализовал — валидация покрытия
- тихая правка чужого теста «чтобы прошло» — только через тикет
